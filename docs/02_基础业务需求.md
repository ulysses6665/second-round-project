# 02 基础业务需求

## 1. 跟着一张申请走一遍

项目有 1,000 元。小林申请采购传感器，预计花 600 元：

| 操作 | 可用 | 冻结 | 已使用 |
|---|---:|---:|---:|
| 保存 600 元草稿 | 1,000 | 0 | 0 |
| 提交申请 | 400 | 600 | 0 |
| 老师批准 500 元 | 500 | 500 | 0 |
| 财务登记实际花费 460 元 | 540 | 0 | 460 |

草稿不占钱；提交后先留出钱；批准和结算时，多留的钱恢复可用。

**每一步都要满足：总预算 = 可用 + 冻结 + 已使用，三项都不能为负数。**

基础版本只有老师这一级审批，批准后即可结算。

## 2. 每个动作怎样处理

| 动作 | 规则 |
|---|---|
| 保存草稿 | 填写用途和金额，可以修改，不占经费 |
| 提交 | 用途必填、金额大于零；经费足够才冻结并进入待审批 |
| 批准 | 批准金额大于零，不超过申请金额；减额部分立即恢复可用 |
| 拒绝 | 原因必填，释放剩余冻结，结束这张申请 |
| 取消 | 申请人可取消自己的待审批或已批准申请；原因必填，释放剩余冻结 |
| 结算 | 财务填写实际花费，不低于零、不超过批准金额；结清冻结，结束申请 |

补充规则：

- 提交失败时仍是草稿，经费不变。
- 提交后不能直接改原金额、用途、项目或申请人。
- 批准零元应改用“拒绝”；结算零元允许，表示最终没有支出。
- 减额后取消，只释放剩余冻结。例如 600 元申请批准为 500 元，再取消只能释放 500 元。
- 结算一次完成，不做分批结算；已结算不能再次结算、普通取消或改金额。
- 已拒绝、已取消不能恢复办理。以后若做“复制为草稿”，应创建新申请，保留旧记录。

## 3. 谁可以操作

| 角色 | 操作与范围 |
|---|---|
| 成员 | 在自己加入的项目申请，只能修改、提交、取消和查看自己的申请 |
| 老师 | 查看并审批负责项目的申请，不能审批自己 |
| 财务 | 查看分配项目的申请，只能结算已批准申请 |
| 管理员 | 管理基础配置，不自动拥有业务查看、审批或结算权限 |

成员可以看所在项目的经费摘要，不能因此看别人申请的详情。老师、财务可以查看各自项目范围的成员信息；普通成员查看本人参与信息即可。

提交时找不到合法审批人，应提示配置问题，不能冻结经费。

## 4. 申请有哪些状态

| 状态 | 代码名称 | 下一步 |
|---|---|---|
| 草稿 | DRAFT | 修改或提交 |
| 待审批 | PENDING_L1 | 批准、拒绝或申请人取消 |
| 已批准 | APPROVED | 结算或申请人取消 |
| 已拒绝 | REJECTED | 查看 |
| 已取消 | CANCELED | 查看 |
| 已结算 | SETTLED | 查看 |

最后三种状态表示这次办理结束。

## 5. 数据与页面要求

- 只用人民币，金额最多两位小数；多于两位要报错，不悄悄舍入。
- 总预算由初始数据给定，基础版本不做预算调整。
- 原申请、批准、实际结算金额分别保留。
- 后端检查金额、状态和权限。操作人来自登录信息，不能相信请求里随意填写的用户 ID。
- 一次操作整体成功或失败，不能出现“还是草稿，经费却被冻结”。
- 页面逐步提供项目经费、我的申请、老师待审批、财务待结算。
- 未结算显示“尚未结算”，实际零元显示“0 元”。
- 操作中有反馈，失败保留输入并说明原因，刷新后仍能看到真实结果。

刚学 Java 时可以先用控制台演示；学到数据库事务和接口后，再逐步补齐。金额可使用整数“分”或 BigDecimal；登录基础代码可以使用课程示例并注明来源。
